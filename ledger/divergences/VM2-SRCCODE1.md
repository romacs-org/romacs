## Observable by a package

| # | mechanism | GNU | romacs | why |
|---|---|---|---|---|
| VM2-SRCCODE1 | Source file coding in `load` | `load` of a `.el` file goes through `load-source-file-function` (`load-with-code-conversion`, `lisp/international/mule.el`): `insert-file-contents` decodes it by the `coding:` cookie or, without one, by `set-auto-coding` and the detection walk over `coding-system-priority-list` (pinned GNU batch: a file of valid UTF-8 is `utf-8`, `caf\xe9` is `iso-latin-1`, `x\x85y` is `japanese-shift-jis`, and `leim/quail/Punct.el`, whose comment holds two stray GB2312 bytes, is `raw-text`, so its strings read as unibyte bytes). GNU's `utf-8` and `utf-8-emacs` share `decode_coding_utf_8` (`src/coding.c:1270`): characters beyond Unicode up to MAX_CHAR decode (`quick-cns.el`'s U+114019), and a byte that starts no character is a raw-byte character | The loader decodes source itself (`crates/romacs-vm/src/loader.rs` `decode_source`), from a cookie in the first two lines: `utf-8` and `utf-8-emacs` through a transcription of `decode_coding_utf_8`, Latin-1, US-ASCII, and the `-unix`/`-dos`/`-mac` EOL variants; any other named system is refused. Without a cookie, bytes that decode as UTF-8 with no raw byte are UTF-8 (GNU's walk finds UTF-8 first); any other file is decided by the same detection walk `insert-file-contents` uses (`prim/leaf/coding.rs` `coding_detect`, VM2-FILEIO1) and decoded by the chosen system, so Latin-1, raw-text (`leim/quail/Punct.el`) and Shift-JIS sources read as in GNU (`tests/source_detection.rs`); a system VM2 cannot decode (ISO-2022, emacs-mule) refuses, and the bare registry, where no category has a system, decides raw-text, which only mule-conf.el defines. Raw-byte and beyond-Unicode characters keep their codes in symbol names as in strings: VM2's Rust-side symbol keys carry them through an injective escape (`crates/romacs-vm/src/symkey.rs`) that `symbol-name`, `intern`, `intern-soft`, `unintern`, `make-symbol`, the printer and `format` decode (a symbol argument is looked up by its decoded name; the printer escapes every piece of Lisp text it copies, so its output decodes only symbol escapes), so Lisp sees GNU's names, identity and printed text (`raw_bytes_in_source_symbols_keep_their_characters`, `tests/symbol_names.rs`); `intern` of a unibyte name with bytes above 127 is still refused (`not-unicode-string`) | **Package-observable:** a cookie-less ISO-2022 or emacs-mule source fails to load where GNU decodes it; none is in the GNU tree | <!-- symbols: load, load-with-code-conversion, load-source-file-function -->

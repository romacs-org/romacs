## Observable by a package

| # | mechanism | GNU | romacs | why |
|---|---|---|---|---|
| VM2-COMPLETE-DEFAULT | Interactive sessions show the minibuffer and completion in a layer, by deliberate default | GNU's interactive default displays `completing-read` in the minibuffer window with `*Completions*` on TAB; Romacs's defaults file used to turn on `fido-vertical-mode`, which grows the mini-window | An interactive `--loadup` session makes `romacs-complete-mode` t a standard value before the user's init (`lisp/romacs/romacs-completion-defaults.el`, in place of `fido-vertical-mode`): prompts and their candidates show in a layer (VM2-MINI-COMPLETION-LAYER) and no window or terminal resizes for a prompt. Without a window system (a layer is a child frame) or where the mode is absent (GNU loading the file for a parity harness) the file turns `fido-vertical-mode` on as before. Batch and noninteractive runs never load the file. A user init overrides it: `(romacs-complete-mode -1)` returns the minibuffer line, and `(fido-vertical-mode 1)` with the mode left on gives icomplete's display inside the layer. Parity harnesses that compare with GNU pin GNU's fido-vertical state in both engines (`parity_live.GNU_COMPLETION`). `harness/completion_live.py` (and `--fido`), `harness/completion_perkey_live.py` | **User-observable**: every prompt is a layer over the frame; packages observe VM2-MINI-COMPLETION-LAYER's answers by default | Deliberate Romacs default: completion as a layer over the frame; per-key cost measured within its budget on the 5k-file fixture (C-x C-f, see the commit) | <!-- symbols: romacs-complete-mode fido-vertical-mode -->

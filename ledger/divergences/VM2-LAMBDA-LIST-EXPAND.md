## Residual interpreted macro calls — KNOWN, PARKED and UNFIXED

| # | Mechanism | GNU | Romacs | Why |
|---|---|---|---|---|
| VM2-LAMBDA-LIST-EXPAND | When a `(lambda ...)` list called as a function expands its macros | GNU's `funcall_lambda` interprets the list (`src/eval.c`): its body's macro calls expand at each call, so an expander that reads dynamic state could expand differently from call to call; a closure's body is expanded once, when the closure is made (`cconv`), and compiled code at compile time | Romacs compiles the list once (`Vm::lambda_list_closure`, `crates/romacs-vm/src/source_cache.rs`) and reuses that code at the next call while the list still has the text it was compiled from (conses, strings and vectors compared by contents, other objects by identity) and no function cell has changed since (the world epoch every `defun`, `defmacro`, `defalias` and `fset` advances): a `setcar` into the list, an `aset` into a literal, a redefined macro or a function that became a macro takes effect at the next call. The body's macros, its inner lambdas' too, expand once per definition, as a closure's do; in GNU's dynamic dialect every binding is dynamic, so a special declaration changes nothing the list compiled to. A list larger than 4096 items, or circular, is compiled at each call. Rust ts mode's `rust-ts-mode--fontify-pattern` (a `defalias` of a backquoted list) costs 240 µs per call compiled each time | A macro whose expansion depends on dynamic state, inside a lambda list called repeatedly, expands with the state of its first call. Tests: `crates/romacs-vm/tests/lambda_list_call.rs` (against pinned GNU) | <!-- symbols: funcall, apply, run-hooks, defmacro -->

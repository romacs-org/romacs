Romacs has no interpreter: `eval`, `eval-expression`, `ielm` and `load` of source compile, so where GNU's interpreter would see a redefinition of `car`, Romacs behaves as GNU's compiled code. `(funcall 'car x)` is not folded and reads the cell (GNU compiled: the byte code). `(+ x y z)`, and the same three-argument `-`, `*`, `min` and `max`, with no number among the arguments, is `(+ (+ x y) z)`: two byte codes, as `byte-optimize-plus` and its siblings rewrite it (`lisp/emacs-lisp/byte-opt.el:917`). Any other call with an argument count GNU does not compile to a byte code (`(car a b)`, `(+ a b c d)`, `(max)`) is an ordinary call and reads the cell. Rationale: a small set of primitives whose semantics cannot be changed is accepted Elisp practice (`bytecomp.el`'s own open-coding), and the per-call guard it replaces was 9% of `ert-tests.el`'s instructions and 2% of the GUI journey's; measurements in the commit. No `gnu-lisp/`, `rlisp/` or test code redefines a byte-op name except fixtures that probe the redefinition itself (`evidence/text-known-answers.json`, re-recorded from compiled GNU).

## Observable by a package

| # | mechanism | GNU | romacs | why |
|---|---|---|---|---|
| VM2-PROJECT-LIST1 | Where `project-list-file` points, and the list an earlier Romacs kept | GNU preloads no project.el: `project-list-file` takes its standard value, `(locate-user-emacs-file "projects.eld")`, when the library first loads, after startup named the per-user directory. | Romacs's chain loads project.el (flymake's `(require 'project)`), so `project-list-file` is a delayed variable (lisp/romacs/romacs-loadup-bootstrap.el): startup computes it in each process once the per-user directory is known, and it names the file GNU's does. Earlier builds computed it against the working directory, so a session started in the home directory kept its list at `~/projects.eld`. The interactive startup (lisp/romacs/romacs-gui-loadup.el) copies that file to `project-list-file` when the new file does not exist and the old one is a readable regular file, and leaves the old one in place (`romacs--migrate-project-list`); a failure is reported in `*Messages*` and startup goes on. A batch session does not copy: its startup also runs inside world builds, which may write no file, and a batch session writes the list only when a script calls project's commands. Such a script, run before the first interactive session, starts a new list, and the old one stays where it was. `test/romacs/lisp/romacs-loadup-bootstrap-tests.el` covers the old file alone, both, neither, and an unreadable or directory old file | The project list is the user's data: a fix to where it lives must not lose it | <!-- symbols: project-list-file, romacs--migrate-project-list -->

## Native leaf batch boundaries

| # | Scope | GNU | VM2 | Reason / evidence |
|---|---|---|---|---|
| VM2-USERSIG1 | User signals (SIGUSR1, SIGUSR2) | keyboard.c `handle_user_signal` turns each into a `sigusr1` or `sigusr2` event (kbd_buffer_get_event), which read_char runs through `special-event-map` or returns as input; when the signal's name is `debug-on-event` (`sigusr2` by default) it enters the debugger at the next quit check instead | The GUI and batch binary and the GNU test runner count both signals (`host::catch_user_signals`) and read_char's Lisp half (lisp/romacs/vm/keyboard.el) reads a pending one as its event, before the host's, a special one running its binding. Different: `debug-on-event` is not consulted, so SIGUSR2 is an event like SIGUSR1, and nothing wakes a wait for a signal: a batch read takes one at once, but the GUI, whose own loop waits for host input, takes it when its command loop next reads a key, not while idle. An isolate worker keeps SIGUSR1 as its interrupt (isolate.rs) | **Visible** to a user who sends SIGUSR2 to a hung session expecting the debugger, and to a GUI session sent a user signal while idle, which handles it before its next key. Test: `crates/romacs-gnu-tests/tests/real_harness.rs` `real_mode_reads_a_user_signal_as_an_event`, against pinned GNU's `(nil (usr1))` | <!-- symbols: special-event-map, debug-on-event, signal-process -->

## Observable by a package

| # | mechanism | GNU | romacs | why |
|---|---|---|---|---|
| VM2-KM1 | VM2 keymap skeleton is installed lazily | GNU builds `global-map`, `esc-map`, `ctl-x-map`, `function-key-map`, `key-translation-map` and `special-event-map` while loading `lisp/subr.el` and `lisp/bindings.el`, so by the time any user Lisp runs these variables are already bound to keymaps (`src/keymap.c:syms_of_keymap` defines the variables; the maps themselves come from Lisp) | VM2 boots without loading `subr.el` and installs the same skeleton on **first use of any keymap primitive** rather than in `Vm::new`. Reading `global-map` (or the other five) before calling any keymap primitive signals `void-variable`, where GNU returns a keymap; after any keymap primitive runs, the variables are bound and behave as GNU | **Package-observable** only by Lisp that reads one of these six variables without first calling a keymap function, which `bindings.el` and ordinary configuration do not do. Chosen so a freshly constructed VM allocates nothing: the collector's tests assert exact heap contents and arena indices, and a constructor-time skeleton silently redefines "empty heap" for all of them. Revertible by calling `initialize_keymaps` from `Vm::new` and converting those GC tests to arena-relative indices | <!-- symbols: global-map, esc-map, ctl-x-map, function-key-map, key-translation-map, special-event-map -->

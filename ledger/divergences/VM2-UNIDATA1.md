## VM2 GNU bytecode representation

| # | Mechanism | GNU | Romacs | Why |
|---|---|---|---|---|
| VM2-UNIDATA1 | Unicode property table functions | `admin/unidata/unidata-gen.el` byte-compiles its runtime functions into eight generated tables (`international/uni-name.el`, `uni-old-name.el`, `uni-comment.el`, `uni-decomposition.el`, `uni-category.el`, `uni-combining.el`, `uni-bidi.el`, `uni-brackets.el`): extra slots 1-3 of each `char-code-property-table` hold byte-code objects. | Those slots hold the symbols of the same functions in source, `rlisp/romacs-unidata.el`, and each of the eight files first requires that library. `tools/lib/romacs_unidata.py` derives the files from the pinned GNU build's output, replacing only the `#[...]` spans. Every other generated `uni-*.el` file is the pinned build's bytes. Verified on all 1,114,112 code points in pinned GNU (`get-char-code-property` and `char-code-property-description` against stock tables), and on Romacs for 16 properties over U+0000-U+2FFFF. | VM2 runs Lisp from source (VM2-EV5, VM2-BYTECODE1); compiled code inside data files cannot be read. **Package-observable:** `(char-table-extra-slot (unicode-property-table-internal 'name) 1)` is the symbol `romacs-unidata-get-name`, not a byte-code object, and the `romacs-unidata-*` functions are fbound. | <!-- symbols: get-char-code-property, char-code-property-description, unicode-property-table-internal -->

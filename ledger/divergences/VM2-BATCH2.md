## Observable by a package

| # | mechanism | GNU | romacs | why |
|---|---|---|---|---|
| VM2-BATCH2 | `emacs --batch` command line and `kill-emacs` | GNU emacs.c takes `--batch`, startup.el `command-line` the leading options (`-Q`, `-q`, `--no-site-file`, ...), then `command-line-1` runs `-L`, `-l`, `-f`, `--eval` and the rest and `(kill-emacs t)` ends the session (`lisp/startup.el:1748-1751`); an uncaught error goes to `command-error-function`, whose batch default prints it and exits 255. `Fkill_emacs` (`src/emacs.c:2953`) runs `kill-emacs-hook` (safe_run_hooks in batch), stuffs a string ARG as terminal input, re-executes Emacs for RESTART, and exits with an integer ARG's code, else success | `romacs-vm-gui [-Q] --batch ARGS...` runs the GNU-loadup chain `--loadup` shares with the batch package runner, on GNU's 80x25 batch frame, restored from its batch world (`src/batch.rs`), takes the same leading options, then GNU's own `command-line-1` over the rest, then `(kill-emacs t)`; errors reach `command-error-function` as keyboard.c cmd_error sends them. The rest of `command-line` is not run: no `site-run-file` load and no package activation (a batch session loads no init file either). `--batch ROMACS_LISP_DIRECTORY` stays Romacs's stdin test runner. `kill-emacs` (`src/prims/emacs.rs`) runs the hook as safe_run_hooks in batch and through `run-hook-query-error-with-timeout` interactively, as GNU does, exits 0 for a string ARG, refuses RESTART, and without a session host (a library embedder, `romacs-gnu-ert`) signals `VM2 kill-emacs without a session host is unsupported`. The batch entry and the live GUI attach one; the GUI's drops the VM, hanging up its children as shut_down_emacs does, closes the window and exits with the status, so C-x C-c (`save-buffers-kill-emacs`) asks to save, runs `kill-emacs-query-functions` and `kill-emacs-hook` and exits as GNU does (`harness/command_errors_live.py`). The workspace GUI without GNU Lisp quits through its own `romacs-gui-quit`. `romacs-gnu-ert --invocation EMACS` names the executable its tests spawn as `invocation-name`. `-nw` (a terminal session) is not a batch command line and stays refused | **Package-observable**: a batch session restores its world, the chain up to GNU's dump point, and takes the startup steps in its own process: about 0.48 G instructions where GNU's start takes 0.23 G, under any HOME and locale. The installation's world (`EXECUTABLE.worlds`, which the installer's `--world-build --batch` builds) serves first and is only read; then the user's store, which `--world-build` fills beside the GUI's world. A world still binds what the chain reads of its builder's user and machine (the login name and uid, `SHELL`, the system name): a session of another user or shell boots the chain from source (some 10 s; gnosis waits 15 s for model preparation), and a background builder prepares its world when the user's store exists already (a fresh HOME gets none), keeping the three most recent per executable. `crates/romacs-vm-gui/tests/batch_command_line.rs` compares exit statuses and output with pinned GNU for `-L`/`-l`/`-f`/`--eval`, `command-line-args-left`, `kill-emacs-hook` and an uncaught error (its message; the batch backtrace is VM2-ERRTEXT1); `tests/kill_emacs.rs` covers the hook, codes and refusals | GNU's C sets `user-login-name` and `shell-file-name` in each process (init_editfns, init_callproc); were they per-process here, one installed world would serve every user and shell | <!-- symbols: kill-emacs, kill-emacs-hook, command-line-1, invocation-name, invocation-directory -->

#+title: The agent session protocol: one interface, several clients

Romacs runs coding agents as sessions.  This document designs the one
interface every client of those sessions uses: the editor on the machine
that runs them, an editor on another machine, and a web page on a phone.
It states the protocol as it is today, decides where the new one is
served, specifies version 1, the relay that makes it reachable over a
tailnet, the clients, and the order of the work.  Status: slice 0 built.

* Requirements

- *One protocol.*  One explicit, versioned, documented protocol is spoken
  by every client:
  - the local Romacs UI, over a Unix socket;
  - Romacs on another machine;
  - a phone page.

  There is no second agent system, and no per-client access path (no
  store read over ssh, no Lisp evaluated in another editor).
- *Reachable on the tailnet.*  A relay serves the protocol over
  WebSocket, published only on the tailnet with =tailscale serve=, and
  takes the caller's identity from Tailscale.
- *Pending first.*  Pending approvals and questions are first-class
  protocol state, shown prominently by every client.  Nothing is answered
  on the user's behalf unseen.
- *Transport-agnostic.*  The Romacs client is the same over a local socket
  and over the relay.
- *Never block.*  Nothing blocks an editor's main VM on the network (the
  one-second rule).  Slow links get bounded transfers and resumable
  streams.
- *Full authority.*  Agents act with the user's authority: a remote client
  gets no reduced tool set.

* The protocol as it is (v0)

** The supervisor: =romacs-agent-host=
=crates/romacs-mcp/src/host.rs= (1,329 lines) runs one harness per
session, owns its stdio, and keeps every line as a record:
=events= rows in =sessions.sqlite= (=--store=), or =journal.jsonl= for a
session not yet imported.

- *Records:* ={"seq":N,"t":T,"out"|"in"|"note"|"exit":...}=.  A line that
  parses as JSON is kept as JSON.  Thinking-token counter lines are
  dropped in SQLite.  A record that ends a turn (Claude =result=, Codex
  =turn/completed=), a note and an exit are synced.
- *Socket:* =$XDG_RUNTIME_DIR/romacs/agents/KEY/host.sock=.
  - The server's first line is ={"attach":{"from":N,"steal":B}}=.  The
    host replays every record from seq N inclusive, then acknowledges
    with ={"attached":ID}=, or ={"attached":ID,"notesOnly":true}= from a
    notes-only host.  After that it sends each new record.
  - ={"write":LINE[,"journal":LINE]}= is journaled as =in= and written to
    the harness's stdin, journal first.
  - ={"note":OBJ}= is journaled as =note=.
  - The host may also say ={"refused":"attached"}= and
    ={"storage":"failing"}=.
- *One attachment at a time.*  Another is refused unless it steals, which
  closes the first.
- *Around it:* notes-only hosts, =--input= per-turn runs,
  =--stage=/=--hold=/=--supervised=, and the session lock (=host.lock=).

** The attached editor: where meaning lives
The host knows no harness format.  The editor attached to a session gives
its lines their meaning, in Lisp.

- *Drivers.* =romacs-agent-claude.el= (799 lines) and
  =romacs-agent-codex.el= (684):
  - =:events= and =:input-events= turn records into normalized events:
    =session=, =input=, =delta=, =message-end=, =thinking=, =tool=,
    =approval=, =answered=, =plan=, =status=, =error=, =compacted=,
    =usage=, =rate-limit=, =done=, =exit=, =suggestion=, ...;
  - =:input=, =:respond=, =:interrupt= and =:select= compose the lines
    written back.
- *The fold.* =romacs-agent--record= and =romacs-agent--raise=
  (=romacs-agent.el=, 6,022 lines) fold those events into a session
  struct: state, approvals, asks, questions, model, effort, context, cost,
  queue, turns.
- *Automation.* The attached editor also:
  - dispatches the queue;
  - writes notes (selection, rename, renew, rollback, fork, resume
    schedule);
  - runs startup steps and keeps the folded state;
  - answers requests nobody was asked about (=romacs-agent--answer-unasked=):
    under =romacs-agent-approval-policy= =allow= it allows tool calls, and
    it denied tool calls in plan mode and denied presented plans.

  None of those answers was drawn.  That path plausibly explains approvals
  reported rejected that the user never saw; the affected records would
  confirm it.  The chat rebuild removes both deny arms and records who
  answered each request.
- *Store writes.* The host writes =events=.  The editor's writer worker VM
  writes =sessions=, =turns=, =turn_drawn= and the folded state.
- *Harness tools.* Each harness runs =romacs-mcp --reconnect= as its Romacs
  MCP server.  Its route link (=route/ID.sock=) leads to the attached
  editor.  The reconnect helper answers discovery and
  =romacs_debug_inspect= itself in documented cases.

  The tools fall into two groups:
  - /Agent tools:/ =romacs_delegate_task=, =romacs_task_*=,
    =romacs_limits=, =romacs_orchestrator_capabilities=,
    =romacs_orchestration_issues=, =romacs_call_outcome=;
  - /Editor tools/, which need a live editor:
    - =romacs_eval=, =_observe=, =_buffer_*=, =_file_write=, =_visit=;
    - =_send_keys=, =_wait_idle=, =_option_*=, =_restart*=;
    - =_dev_check=, =_dev_guide=, =_companion_*=;
    - =gnosis_*=.

** What follows from it
- *One client.*  A second editor is refused, or steals the session and
  breaks the first editor's tools.
- *No client without the drivers.*  A client of the v0 protocol must run
  the drivers, the fold and the policy itself.  A phone cannot.

Measured on 2026-11-19, each figure with how it was taken:
- *Fold rate.*  Folding records into events (driver and fold) runs at
  24,700 records/s: 14,633 records, 8 MB, in 0.59 s.  Gate build of beta
  6c26b7d73, on a Ryzen 9 5950X.  The records were read from a copy of one
  session's events and passed to =romacs-agent--record= on a scratch
  session.
- *Host to fold.*  A host's record reaches the attached editor's fold in
  0.54 ms at the median and 9.5 ms at p95, over 18 live records of one
  turn.  Taken on the 5950X, build d886623c, as =float-time= minus the
  record's =t= in an advice on =romacs-agent--record=, in a private editor
  attached to a private session.
- *Store size.*  The store is 5.5 GB plus a 1.1 GB WAL, and one
  session's records reach 319 MB.

* Where the protocol is served

Something on the machine that runs the sessions must run the drivers and
speak a semantic protocol.  The four candidates, with their costs:

- *(i) Drivers in the host (Rust).*  Each host speaks semantic events
  itself.
  - /Startup/ and /memory/: nothing added.  /Latency/: the lowest.
  - /Cost/: re-implementing the drivers, and the parts of the fold,
    policy, queue and notes the protocol needs, in Rust.  That
    contradicts "Lisp carries policy", and the drivers stop being
    hackable Lisp.
  - /Failure/: per session, but cross-session work (pools, delegation,
    limits, agent tools) has no per-session home.
  - Rejected.
- *(ii-a) The service as a worker VM of the desktop editor.*  A child
  process forked from the zygote.
  - /Startup/: 0.63 to 0.73 s for a fresh worker to load the agent
    layer's features (=isolate-spawn :fresh t :require= of
    =romacs-agent=, its two drivers, store, events, turns, tools and
    =romacs-mcp=).  Measured twice in a private GUI editor on an i5-2520M
    (2011), on beta 6c26b7d73's Lisp with the gl-fallback binary.
  - /Memory/: it shares the editor's pages through the zygote; +25 MB
    measured in the parent's RSS.
  - /Failure/: it dies with the editor (=PR_SET_PDEATHSIG=), so remote
    clients lose the service whenever the desktop editor crashes or
    restarts.
- *(ii-b) The service as its own process* (recommended).  A headless
  Romacs process runs today's Lisp agent layer: drivers, fold, policy,
  queue, notes, store writer, agent tools.
  - /Startup/: 0.43 s.  /Memory/: 180 MB RSS; a bare batch process is
    0.08 s and 94 MB.  Measured three times on the Ryzen 9 5950X, build
    d886623c, with =/usr/bin/time= around =romacs-vm-gui --batch= requiring
    the same features.  The restore that follows costs the fold rate
    above, from each session's folded state.
  - /Latency/: one more local socket hop per event.  That is an estimate
    by analogy with the measured host-to-fold hop (0.5 ms at the median);
    slice 1 measures it.
  - /Failure/: its own; a user unit restarts it (below).
- *(iii) The desktop editor as the service.*  Today's arrangement plus an
  endpoint.  Every remote client depends on the desktop UI process and
  its main VM's stalls.

*Recommendation: (ii-b).*  One agents service per machine is the single
attached server of every host and the single authority for every
session.  Every UI is a client of it through the same protocol, the
local editor included.  Romacs stays a Lisp machine: the service is
Romacs, the drivers stay hackable Lisp.  The host's line protocol
becomes internal (service ↔ host, v0 above) and unchanged, so hosts
started by older builds keep working.

** When the service crashes or restarts
- *Harnesses go on.*  Their hosts keep running and keep recording.  Each
  host runs in its own transient unit (=systemd-run --user
  --unit=romacs-agent-KEY --slice=romacs-agents.slice=, as an editor
  launches it today), never in the service's cgroup, so stopping or
  restarting the service's unit leaves them alone.  The two paths that
  would put a host in the launcher's cgroup are taken out of the service:
  - the =setsid --fork= fallback when =systemd-run= fails;
  - the =setsid= launch of notes-only hosts.

  The service refuses to launch rather than fall back, and says why.  The
  unit's restart test launches a harness from the service and restarts
  the unit.
- *Requests wait.*  A request waiting on an answer (Claude
  =can_use_tool=, Codex approval) waits; the harness blocks on it.
- *Queued messages survive.*  They are kept in the =queued= table, as
  today.
- *The restarted service recovers.*  It restores every session, attaches
  to each live host, and replays from each session's folded state.  An
  unanswered request in the records is pending again.  The command table
  resolves what was in flight (see Commands).
- *Editor tools in flight* are answered =outcome unknown=, as the
  reconnect helper does today.
- *Clients see the connection end.*  They reconnect.  The service's
  generation has changed, so every revision is new: clients watch the
  list again and resume their open sessions from their cursors.
- *The unit* restarts the service (=Restart=on-failure=).  The first
  editor starts the service if the unit is not installed.

* Protocol v1: =romacs-agents/1=

** Framing
- *Messages:* JSON-RPC 2.0.  One message per line on a Unix socket, and
  one per reassembled WebSocket text message through the relay.  Messages
  go both ways: the service sends notifications and, to editors (below),
  requests.
- *Endpoints:*
  - =$XDG_RUNTIME_DIR/romacs/agents/service/service.sock= for local clients;
  - =service-relay.sock= beside it, for the relay alone (below).

  Both are separate from the MCP endpoint the harness relays use.
- *Limits*, on the encoded message, envelope included:
  - a message is at most 1 MiB;
  - a reply is at most 1 MiB encoded.  Its units (below) fill at most
    768 KiB of it.  Everything else in a reply (the envelope, the echoed
    =id=, cursors, tokens, revisions) is bounded so that it is at most
    64 KiB:
    - a request's JSON-RPC =id= is at most 128 bytes encoded;
    - a =cid= is at most 128 bytes;
    - a =more= token and a cursor are at most 1 KiB each.

    A request over those bounds is refused with =-32600=, its =id= not
    echoed when that is what is too long, as the MCP endpoint already
    does.  So a reply never exceeds the limit;
  - every unit is bounded.  A unit is what a reply or a notification is
    made of: a record unit, a pending request, a queue entry, a row, a
    catalog entry.  A string in one is cut to its first 64 KiB, then, while
    the unit is over 256 KiB, to 8 KiB and to 1 KiB; each cut is named
    by its JSON Pointer under its event's =truncated=
    (={"/output": BYTES}=), as long as it was.  A record unit still over,
    or not encodable, is sent as ={"events": [], "oversize": true}=, its
    seq kept.  A pending request, a queue entry and a catalog entry
    are cut alike, their key fields never; one still over is sent as
    its key fields and ="oversize": true=: a request keeps its handle,
    kind and choices, and is answered by its decision; a question that
    needs its options is answered on the agent's host.  A row's strings
    are cut to 1,024 characters.  Nothing is fetched whole: a chat needs
    no more of an output, and the files an agent writes are on its host;
  - an editor tool's result is bounded where it is made: each editor tool
    caps its own output (64 KiB), as the MCP tools do today
    (=romacs-mcp-eval-string= refuses a larger value).  The service never
    fetches a large result from an editor;
  - continuation tokens expire.  A =more= token lives while it is used,
    and dies after 60 s unused or when a connection holds more than four.
    An expired token is answered with =-32017= (=stale=), and the client
    starts the call again.  So a stalled client never pins a snapshot;
  - every reply that returns a collection, of any method, pages by
    units; no method returns an unbounded whole.  That covers the open
    reply's =pending= and =queue=, a history reply's units, the list, and the catalogs (=projects.list= returns projects
    and =providers.list= returns providers as units).  A method added
    later follows the same rule.  Each reply holds
    whole units and at least one of them, since a unit is at most
    256 KiB, so every continuation (=more=) advances.  A reply that
    doesn't fit carries the first part and =more=;
  - a list notification still over 1 MiB after that is sent as
    ={"revision","stale":true}= in its place: the client watches again
    from the revision it holds, a reply that pages.  A row's strings
    are cut to 1,024 characters, so a row is a small unit.

** Handshake and versions
- *Hello.* =agents/hello= must come first.  Its params:
  - ={"protocol":"romacs-agents","version":[1,MINOR]}=;
  - ="client":{"name","version","instance"}=, where =instance= is a UUID
    the client keeps across reconnects;
  - ="capabilities":[...]=.
- *Welcome.* The reply:
  - ={"version":[1,M]}=, with M the lower of the two minors;
  - ="server":{"host","build","generation"}=;
  - ="identity":{"via":"local"|"tailnet","login"}=;
  - ="capabilities":[...]=, =capabilities= being the intersection.
- *Before the hello,* every other method is refused (=-32002=, not
  initialized).
- *Majors.* A major mismatch is refused (=-32013=), with the version
  served in =data.served=.
- *Minors.* Within a major, a minor adds optional fields, events,
  methods and capabilities.  Never a changed meaning.
- *Must-ignore.* A client ignores an unknown event type or field.  An
  ignored event never invalidates the client's state: everything a
  client must know to stay consistent (rows, pending requests, queue,
  resets) comes in the core messages below, never only in an event type
  it may not know.

** Errors
JSON-RPC errors with numeric codes and =data.kind=:

| code   | kind             | meaning |
|--------+------------------+---------|
| -32602 | bad-params       | malformed params |
| -32002 | not-initialized  | no hello yet |
| -32010 | unknown-session  | no such session |
| -32011 | request-gone     | the request is answered, settled or gone; =data.resolution= says how |
| -32012 | not-live         | the session has no running harness for this command |
| -32013 | unsupported      | this harness or version cannot do it |
| -32014 | forbidden        | the identity may not |
| -32015 | cid-conflict     | a client id reused with a different command |
| -32016 | busy             | the session is changing hands (handoff); retry |
| -32017 | stale            | a continuation token expired; start the call again |
| -32603 | internal         | with a message |

** Generations, revisions and cursors
- *Generation.*  A service process names itself with a generation, a UUID
  made at start, in the welcome.  Every revision below is scoped by it:
  a client that sees a new generation drops its revisions and watches
  again.
- *List revision.*  One counter per generation, raised by every change to
  any row.
- *Session revision.*  One counter per open of a session on a connection,
  from 0 in its reply, raised by each notice of it: a record's events, a
  pending request added or resolved, a row or queue change.
- *Session cursor.*  A cursor is ={"seq":N,"epoch":E,"adapter":A}=.
  - =N= is the seq of the last record whose events were delivered.  A
    seq is one unit: of records sharing one (legacy staged journals have
    a few), the first is folded, as the editor folds them.
  - =E= is the session's epoch, 0 for none (=epochs= in the store).  A
    record's events depend on the records before it: a streamed
    message's whole record raises no text, its deltas having raised it.
    Compaction removes those deltas, and the whole record then raises the
    text, so a client resuming after a delta would draw it twice
    (=romacs-agent-events-compaction-changes-what-follows-a-seq=).  So
    every transaction that deletes any of the session's records raises
    the epoch in that same transaction, as does the flip that moves the
    session's reader from its journal to SQLite.  A cursor or a page
    read before either always carries an older epoch.
  - =A= is the adapter version: a digest of the driver that made the
    events.
- *Epochs are read where history is.*  An open and each page carry the
  cursor with its epoch and adapter; a page of another than the open's
  makes the client discard its history and open again.  A live event
  carries its seq alone.  Records a client was sent live can still be
  compacted once the harness stops; its next history read sees the
  epoch move.
- *A client's resume cursor* is the end of what it holds without a gap:
  the highest seq below which it holds every record unit.  Live events
  past a gap it is still pulling never advance it, so a second
  disconnect resumes from before the gap.
- *Resume.*  A client resumes by reopening: it gets the state at once,
  and pulls the records after its old cursor as history (Pages); answered
  =reset=, it draws the session afresh from the last turns.

** Delivery order
- *Per connection, in order.*  For each subscription (the list, or one
  session), the service writes a reply before any notification belonging
  to it.  It writes that subscription's notifications in revision order,
  each carrying its revision.
- *Reply first.*  A subscription's reply is written before its first
  notification.  Nothing is held back after the reply: a reply that
  continues (=more=) is completed from a copy the service keeps, while
  notifications flow.
- *Applying.*  A client applies a notification only if its revision is
  the one after the revision it holds.  It ignores one at or below that
  revision.  On a gap it re-opens.

** The session list
- *Watch.*  =agents/sessions.watch {since?, generation?}= answers, in
  one call, with ={"revision","rows","removed","reset","more"}=:
  - with no =since=, or one whose =generation= is not the service's,
    every row;
  - with one, the rows changed after it and the ids removed (tombstones,
    kept for the generation).
  A row changes when its session raises an event, when the store's row
  is written by another process, and on a whole pass each minute.
- *More.*  When the reply is cut, =more= is a token.
  =agents/page {more}= continues any paged reply: the list's at the same
  revision, from the copy the service keeps for the token's life, a
  session's, a catalog's.  A client reads notifications meanwhile and
  applies them once it holds the whole reply.
- *Notifications.*  =agents/sessions.changed {revision, rows, removed}=.
- *Row (normative):*
  #+begin_src json
  {"id": "...", "title": "...", "cwd": "...", "project": "...", "parent": null,
   "harness": "claude", "provider": "claude", "model": "...", "effort": null,
   "state": "starting|running|waiting-approval|idle|detached|unstarted|ended",
   "key": "working", "pending": 0, "queued": 0, "activity": null, "turn_start": null,
   "input_seq": 0, "done_seq": 0, "seen_seq": null, "settled_seq": null, "failed": false,
   "last_time": 0.0, "cost": null, "context_used": null, "context_window": null,
   "children": 0}
  #+end_src
  Every field is present; =null= means unknown.  =key= is the session's
  state as this machine's board shows it (=romacs-agent-board--key=),
  made by the service alone: a client draws it, never derives it.
  =pending= counts the session's pending requests.  The seqs are those a
  store row keeps: a client makes its session of a row as a row's is made.

** One session
Live state and history are separate.  Live state is small, and is
delivered at once.  History is immutable, and is pulled in pages.  No
paging ever holds live delivery back.

- *Open.*  =agents/session.open {id}=.  The service, on its main VM and
  atomically, registers the subscription and captures the session
  revision V, the cursor H of its last record kept and the state: row,
  pending and answering requests, queue.  Opening reads: a session not
  loaded stays so, and has no live events until an editor loads it.
  Live events follow H for this subscription alone: a unit at or below
  it (a supervisor's replay on attach) is never sent it.  The reply:
  #+begin_src json
  {"revision": V, "cursor": H, "row": {}, "pending": [], "answering": [],
   "queue": [], "undelivered": [], "more": null}
  #+end_src
  A queue entry is ={"id","text","mode":"now|next|steer","position","images":[]}=.
  An item under way at H (a tool, a message) is drawn from history.
- *Notifications follow at once*, in revision order from V+1, whatever
  the client does next:
  - =agents/event {session, revision, seq, events, gap?}=: the events
    of one record unit.  A load that folded records with no events (a
    worker's fold, a journal read with no supervisor) is sent at once as
    an event with no events and =gap {after, upto}=: the records with
    =after < seq ≤ upto=, which the client pulls as history;
  - =agents/pending.added {session, revision, request}=;
  - =agents/pending.answering {session, revision, handle}=;
  - =agents/pending.taken {session, revision, handle}=;
  - =agents/pending.resolved {session, revision, handle, how, ...}=;
  - =agents/session.changed {session, revision, row}=;
  - =agents/queue.changed {session, revision, added, removed}=: queue
    entries added, and the ids of those removed.  A queue change is a
    delta, never the whole queue.
- *State too large for one reply* (a long queue, many pending requests)
  says =more=.  =agents/page {more}= returns the rest of the same state
  at V, which the service keeps for the token's life.  The client reads
  its notifications meanwhile but applies them only once it holds the
  whole state.  The buffering is the client's; the service holds
  nothing back.
- *History* is pulled separately (see Pages):
  - the last turns up to and including H, for a fresh open;
  - for a reopen after a disconnect, the records with =OLD < seq ≤ H=
    (=agents/session.history {after: OLD, upto: H}=).

  Live notifications start after H, so history and live delivery meet
  without a gap or an overlap.

  A client draws history above the live part, which it has already
  drawn from the state and the notifications.
- *Close.*  =agents/session.close {id}=.
- *Overflow.*  Each connection has a 4 MiB send buffer of notifications.
  Only a client that stops reading its socket can fill it.  The service
  then closes the connection, and the client reopens: state at once,
  history pulled.  A closed connection is the one overflow signal that
  cannot be lost.

** Pages
- *Method.*  =agents/session.history {id, upto, after?, turns?, records?}=,
  its bounds =after < seq ≤ upto=:
  - without =after=, the last =turns= turns (3 by default, 50 at most)
    ending at =upto=, from where a chat of them begins
    (=romacs-agent-tail-start=): no more than =records= records (20,000,
    also the most), within a turn longer than that;
    =upto= set to just before the first unit goes further back;
  - with =after=, every record unit in the range, folded from its turn's
    start however far back.  A range over 4,000 records answers =reset=:
    the client draws the session afresh.
- *Read as live.*  The service replays from the first record of the turn
  the range begins in, so each unit's events are those live delivery
  sent (a message's text never twice), between the editor's other work.
  A reply's units can begin mid-turn, after units the client holds.
- *Reply.*  ={"cursor": {seq, epoch, adapter}, "units": [{seq, events}],
  "from", "reset", "more"}=, paged by units; =from=, for a read without
  =after=, is the seq its records begin at, =null= at the session's start.  Past 8 MiB of units it stops, its
  cursor's seq where: the client asks on from there.  The epoch is read
  before and after the replay: moved, the reply is =reset=.  A client
  compares a reply's epoch and adapter with those its history was read
  under, and draws afresh on any other.  A session still in a journal
  (one an install found running) has none served (=unsupported=).

** Pending requests
- *Request (normative):*
  #+begin_src json
  {"handle": {"run": 0, "id": "r17"}, "session": "...",
   "kind": "tool|question|plan|permissions", "since": 0.0,
   "origin": null,
   "tool": {"name": "...", "input": {}, "reason": null},
   "questions": [{"id": "q1", "text": "...", "header": null,
                  "select": "one|many", "free_text": false,
                  "options": [{"id": "o1", "label": "...", "description": null}]}],
   "plan": null,
   "choices": [{"decision": "allow|deny", "scope": "once|turn|session"}]}
  #+end_src
  - =tool= is the call that asks; =questions= and =plan= are present as
    the kind needs, else =null=.
  - =handle.run= is the seq of the harness run's =run= note, so a
    request id reused by a later run is a different request.
    =handle.id= is the service's short id for the request; the harness's
    own request id, of any length, stays in the service.
  - =choices= lists what this harness accepts for this request:
    - Claude: allow once, allow for the session, deny with a reason;
    - Codex: accept, accept for the session, decline; permissions in
      =turn= or =session= scope.
- *Arriving and leaving.*  A request arrives as =pending.added=.  It
  leaves only as =pending.resolved {session, revision, handle, how,
  actor, decision, scope, reason, answers}=.  =how= is one of:
  - =answered=: by a user or by policy;
  - =harness=: the harness settled it (Codex =serverRequest/resolved=);
  - =turn-end=: the turn ended with it open;
  - =exit=: the harness exited.  Today that is a silent =clrhash=; the
    service emits one per request;
  - =reset=: a fresh snapshot follows.

  =answered= means the answer was recorded by the host.  Whether the
  harness acted on it shows in the harness's later events (the tool's
  result, a turn's end), never in the resolution.
- *Answering.*  The v0 host records an answer before it writes it to the
  harness, and says nothing if the write blocks or fails.  So between
  its =in= record and the harness's next record, an answered request is
  /answering/, not gone:
  - it moves from =pending= to =answering= in the snapshot, and stays
    visible there;
  - it leaves =answering= (=agents/pending.taken=) only on evidence about
    that answer:
    - the host's =written= record for the answer's =in= record (below);
    - the harness settling that request;
    - the turn ending;
    - the harness exiting.

    Unrelated harness output never clears it.
  - a client shows an answer still answering after 30 s as "not taken by
    the harness yet".  It offers the one recovery that does not need the
    harness's stdin: stop the harness (its unit stopped, as =agents/stop=
    does), then resume;
  - the service never sends an answer again by itself.  The user may,
    with =agents/answer {..., again: true}=, which is accepted only for a
    request still answering.  A harness that closes
  a request it was answered on (Codex =serverRequest/resolved=, also on
  a cancellation) changes nothing more.
- *Plans.*  A presented plan (=ExitPlanMode=) is of kind =plan=: always
  the user's, never answered by policy.
- *The answer's shape:* =answers= maps a question id to
  ={"options": [OPTION-ID ...], "text": STRING-or-null}=: one option for
  =select= =one=, any for =many=, and =text= when =free_text= is set.
- *Attribution.*  =actor= is ={"kind":"user"|"policy"|"harness"|"unknown","login":...,"client":...}=.
  - It is persisted as the chat rebuild persists it.  The answering
    process first writes a note
    ={"type":"answer","request","by","decision","scope","reason","login","client"}=,
    which replays as an =attributed= event; then it writes the response
    line.
  - The note names the harness's request id; with =handle.run=, the
    run it was asked in, that pairs it with its response line.  An
    =answer= note counts as an answer only once that response is
    recorded.  A note whose response never came (the process
    died between them) leaves the request pending, and is drawn as "an
    answer not delivered".
  - The service reads the actor from that note.  An answer without one
    (older records, the harness's own settling) has =kind= =unknown= or
    =harness=.
- *Closing by the harness.*  A request the harness closes before any
  answer resolves with =how= =harness=.  Codex's adapter must emit that
  event whenever =serverRequest/resolved= comes for a request still
  pending (slice 1).
- *Policy.*  It runs only in the service.  Every answer it gives is
  resolved with actor =policy= and drawn by every client.  Nothing is
  denied on the user's behalf.

** Commands
- *Client ids.*  Every command carries =cid=.  The pair (connection
  identity, client instance, =cid=) names it.
- *The command table.*  =commands= in the store keeps each command by
  its key: a digest of its method and params, and its outcome, kept as
  =unknown= before it takes effect, which waits for that, then its result.  Kept 24 hours, the newest
  10,000 at most, pruned when the editor is idle.
- *Repeats.*
  - A repeated =cid= gets the recorded outcome.  One kept =unknown= (the
    service stopped before its result was kept) is never run again.
  - A =cid= reused with different params is refused (=cid-conflict=).
  - A repeat after its row expired is a new command.
- *Delivery.*  A =send= goes through the session's queue.  The queue's
  items are kept in the store, and the message's =in= record names the
  item it was (=romacsQueued=), so no item goes twice across a restart.
  Its =in= record carries the message's =romacsRequest= tag.
- *Start* (=agents/start=, next): its milestones (=allocated=,
  =launched=, =prompted=) are kept in its row, a repeat reporting the last
  reached.  Every host the service starts gets a unit of its own, never
  an untracked =setsid= launch, and a unit pending or activating counts
  as in flight.
- *With the service in its own process (S6+):*
  - a queued item is marked =dispatching= before it is handed off, and
    an item marked so is never handed off again;
  - when a handoff can no longer give its tagged =in= record, live or
    after a restart, the records are read for the tag: found, the item
    is done; not, it moves to the session's =undelivered= list, its
    command =unknown=;
  - undelivered entries (={"id","text","images","since","cid"}=) are in
    the open reply's =undelivered= and come as =agents/undelivered.changed=;
    clients show each as "may not have been sent", and only the user
    sends it again (=agents/send=) or drops it
    (=agents/undelivered.dismiss=).
- *Admission.*  Each command is admitted atomically at the authority.
  A request is answered once in its run, by whoever answers first: a
  client, the serving editor's user or its policy.  A second answer gets
  =request-gone=, as does a handle of another run.
- *Outcome.*  Each result carries ="state"=:
  - =queued=: held by the service, as a message waiting for a turn;
  - =written=: sent to the host;
  - =recorded=: its =in= record came back.  The host records before it
    writes to the harness, so this proves the line was kept, not that
    the harness acted on it;
  - =unknown=.

  What the harness then did arrives as events.

Served: =send=, =answer=, =interrupt=; the others come in their slices.

| method | params | result |
|--------+--------+--------|
| =agents/send= | =cid id text mode:"now"/"next"/"steer" images?= | =state= |
| =agents/answer= | =cid id handle decision scope? reason? answers?= | =state= |
| =agents/interrupt=, =agents/stop=, =agents/resume= | =cid id= | =state= |
| =agents/start= | =cid cwd prompt? title? provider? model? effort? parent?= | =state id= |
| =agents/select= | =cid id model? effort? provider?= | =state= |
| =agents/plan= | =cid id on= | =state= |
| =agents/rename=, =agents/settle= | =cid id title=, =cid id on= | =state= =applied= or =unknown=, =revision= |
| =agents/reply= | =cid id message text= | =state= |
| =agents/projects.list=, =agents/providers.list= | | ={"projects":[{"cwd","last_time"}]}=; ={"providers":[{"name","harness","models":[{"id","label","efforts"}]}]}= |

- *Unsupported in 1.0 (=unsupported=):* rollback, renew, fork, move to
  another account.  Each gets a method in a minor version.
- *Attachments are references, never copies.*  =images= holds paths: a
  path on the agent's host, or =HOST:PATH= for a file on the client's
  machine, which the agent reads in place, over ssh from its host.
  No file's bytes enter the store, the logs or the wire.  A client
  sends =HOST:PATH= only for a machine the agent's host reaches by ssh;
  the send checks nothing, and a file the agent cannot read is that
  turn's tool error.

** Events
- *Event (normative).*  =agents/event= carries one record unit's events,
  in order.  The schema is =romacs-agent-wire-events=
  (=lisp/agents/romacs-agent-wire.el=).  Every event has =type=, =seq=
  (its record's) and =time=, then each field its type names, =null= when
  it has none; a field's name is the driver's, =_= for =-=.  Other types
  and fields are the editor's own and are not sent.  The types:

| type | fields |
|------+--------|
| =input= | =text images steer own messages request= |
| =incoming= | =text prompt messages= (messages from other sessions) |
| =delta= | =message text parent= (text appended to message =message=) |
| =thinking= | =text parent= |
| =message-end= | =message parent= (the message's deltas are all of it) |
| =tool= | =id name state input output parent= (=state=: =started=, =completed=, =failed=) |
| =tool-output= | =id text= (streamed command output, live only) |
| =task= | =id task state background activity summary title= |
| =status=, =error= | =text parent= |
| =done= | =text error limit interrupted duration cost reason= |
| =exit= | =status= |
| =compacted=, =plan= | =text= |
| =usage= | =context_used= |
| =selection= | =from to= (each ={model, effort, provider}=) |
| =renewed= | =why from to brief= |
| =forked= | =from title seq_from turns after= |
| =rolled-back= | =to turns prompt files= |
| =replied= | =message reply by_user= |
| =unknown= | =raw method= (a harness line Romacs does not read) |
| =approval= | =request parent policy= (=policy=: the serving editor's policy answers it) |
| =answered=, =attributed= | =handle behavior answers=; =handle by decision scope reason answers= |

- *Reading back.*  =romacs-agent-wire-decode= reads an event as it was
  raised: the schema names the fields read back as a name or as data.
- *Vectors.*  =test/romacs/lisp/romacs-agent-wire-tests.el=: a turn of
  each harness, each record with the events sent for it, read back and
  drawn as the chat draws them raised.
- A tool's output is its completed item's, as its harness caps it:
  streamed output is live only; compaction removes it once the item
  completes.

* The relay: =romacs-relay=
A small Rust binary in a new crate, =crates/romacs-relay=, built on
=tungstenite= and =rustls= (both already in the dependency cache).  It
holds no agent logic.

** Serving
- *Socket.*  It listens on a private Unix socket,
  =$XDG_RUNTIME_DIR/romacs/relay/http.sock=, in a directory of mode
  0700.  It is published with
  =tailscale serve --bg --https=443 unix:PATH=, which serves only the
  tailnet.  The setup check (=romacs-relay check=) confirms tailscaled can
  reach the socket.
- *Routes.*  =GET /= serves the phone page.  =/agents= upgrades to a
  WebSocket.
- *Identity, before any message.*
  - The request must carry =Tailscale-User-Login=, which Serve sets for a
    user-owned device and strips from what the caller sends.  It must
    name a login in the allowlist (=$XDG_CONFIG_HOME/romacs/relay.json=).
    A request without it, a tagged device's included, is refused
    (403).
  - The =Origin= header, when present, must be the page's own origin, so
    a page on another site cannot use the user's browser and tailnet
    identity.  A native client sends none.
- *The handoff to the service.*  The relay connects to
  =service-relay.sock= and sends first
  ={"jsonrpc":"2.0","method":"agents/transport","params":{"via":"tailnet","login":...,"peer":...}}=.
  The service binds that identity to the connection, which stays remote:
  it can never register as an editor.  The relay drops any client
  message that names a transport.
- *Threat model.*  One user's machine: any process of that user already
  holds the user's authority.  The Unix sockets keep other users out.

** Connecting
=romacs-relay connect URL --socket PATH= runs on another machine.
- It opens a local Unix socket that speaks the protocol and copies each
  client connection to one WebSocket.
- When the WebSocket drops, it closes the client connection.  The client
  says hello again and resumes, so it never keeps a dead subscription.
- The Romacs client therefore only ever opens a Unix socket, the local
  service's or a bridge's: there is no WebSocket or TLS in Lisp.

* Clients

** The client model: =romacs-agent-client.el=
A passive mirror:
- the list's rows and revision;
- each open session's snapshot, pending requests, queue and
  events;
- one function per command.

It folds nothing and has no policy, no queue dispatch and no timers that
act.  A client cannot answer, resume or send by itself, by construction.

The board and the chat read only through it:
- the chat draws the events and the pending requests;
- the board draws the rows.

This is the refactor at the seam: UI code that reads session structs
moves to the client model's accessors.

** The local editor
- It connects to =service.sock=, as every other client does.
- While the service still runs inside the desktop process (first
  slices), the editor connects to its own process's socket.
- No UI reads the service's structs directly at any stage.

** Romacs on another machine
=romacs-agent-remote-host= names the machine.  The editor:
- starts =romacs-relay connect= as a subprocess;
- opens its socket;
- draws the board and chats as it does locally.

** The phone page
- *What it is:* one static HTML and JavaScript file, with no build step,
  in =assets/agents-web/= and served by the relay.
- *What it shows:*
  - the session list, waiting sessions first;
  - one chat: the events, and each pending request as a prominent block
    with its choices or its questions;
  - a composer;
  - a start form: project from =projects.list=; provider and model from
    =providers.list=.
- *Resuming:* it keeps its cursors and resumes.

** Editor tools from the service
Once the service runs on its own, an agent's editor tool needs an editor.

- *Registering.*  A local editor registers on its connection to
  =service.sock= (=agents/editor.register=, never over the relay).
- *Home editor.*  The latest registration is the home editor, until it
  disconnects or another registers.  A call goes to the home editor at
  the time it is sent, and stays pinned to that editor: a later
  registration does not move it.
- *Calling.*  The service calls the editor with a JSON-RPC request,
  =agents/editor.call {call, session, relay_incarnation, tool, args}=,
  which keeps the session and relay context the caller checks need.
  =agents/editor.cancel {call}= withdraws it.  The editor answers whether
  the call was still queued (=not executed=) or had started (=outcome
  unknown=, its result then dropped).
- *Outcomes:*
  - the editor's result;
  - =not executed=, only when the call was never sent, or the editor
    refused or withdrew it before taking it;
  - =outcome unknown= whenever the call was sent and no answer came: the
    pinned editor disconnected, or died before answering a cancel.
- *Records.*  The service keeps each call's outcome in the command table,
  so =romacs_call_outcome= answers after a service restart.  A call in
  flight when the service died reads =outcome unknown=.
- *No editor:* with none registered, an editor tool is answered
  =not executed: no editor attached=.

* Ownership, races, compatibility
- *One authority per session.*  The service alone writes to hosts.
  Clients command, and the service admits each command against its state
  atomically.
- *Hosts, compatible.*  The service ↔ host protocol stays v0, so hosts
  started by older builds go on working.  One additive change (v0.1,
  slice 1): once a written line has reached the harness's stdin, the
  host journals and sends a record ={"seq":M,"t":T,"written":SEQ}=,
  SEQ being the line's =in= record.  As a record it replays: a service
  restarted after the write finds it.  A v0 host writes none.  Its answers then stay
  =answering= until the turn ends, the request settles or the harness
  exits.  Its limits show in the
  outcomes: =recorded= means the host recorded a line, not that the
  harness acted on it.  A later host change brings a hello with
  capabilities and keeps v0.
- *Cut over in order.*  Moving authority from the desktop editor to the
  service is one ordered handoff:
  1. the editor stops its restore, attach and writer paths;
  2. it drains what it owes (notes, queued writes);
  3. the service restores and attaches;
  4. the routes are relinked to the service;
  5. commands are admitted again, with =busy= returned until then.
- *File ownership across lanes.*  The chat view and the =answer= note
  belong to the chat rebuild.  This work takes their schema, and both
  land against the same spec.
  - Attribution is persisted only in the =answer= note, replayed as
    =attributed=; an earlier =romacsAnswer= field beside the response is
    not.
  - The chat view's history deduplicates by the cursor above (a seq is
    one unit, its first record folded), the same contract as the
    protocol's; its replays fold into copies made the same way
    (=romacs-agent--scratch=), which never act on the live session.

* Slices
Each slice is landable on its own:
- *S0 — the specification.*  This document's v1 as a reference
  (=doc/agent-protocol.org=):
  - the event schema and its vectors (Events);
  - the epoch, raised by compaction and by the flip (Cursors).
- *S1 — the service core*, inside the desktop process:
  - the host's v0.1 changes: the journaled =written= record, and
    =--input-tag= for per-turn prompts;
  - launches tracked in their own units, with no =setsid= fallback for
    hosts the service starts;
  - =romacs-agent-service.el= on =service.sock=: watch, open, history,
    commands with the command table, pending lifecycle, editor-less
    agent tools;
  - =romacs-agent-client.el=;
  - row, request and message encoders beside the event schema, and
    the Codex adapter's =harness= resolution on =serverRequest/resolved=
    for a request still pending;
  - a conformance suite against a private editor with a scripted
    harness:
    - replay racing live output and a queue change;
    - a reconnect across compaction;
    - an oversized event and a paged reply: a unit just over and just
      under 256 KiB with the largest permitted request =id= and token, a
      catalog with a provider over 256 KiB and another entry after it,
      an editor tool result over the budget, an expired continuation;
    - two clients answering one request;
    - a command repeated across a service restart;
    - the extra local hop measured.
- *S2 — the local UI on the client model*, over the socket.  The board
  and the chat move onto the client model, with the chat rebuild; policy
  answers are drawn with their actor.
- *S3 — the relay.*  Serve and connect, identity and Origin checks, the
  page route, and the setup check, with Rust tests against a fake
  service.
- *S4 — the phone page.*  Accepted on a phone over the tailnet.
- *S5 — Romacs on another machine.*  Accepted from it: headless first,
  then the GUI.
- *S6 — authority handoff.*  The ordered cutover above, proved with a
  live harness, a queued message and a pending request across a restart.
- *S7 — the service in its own process*:
  - a user unit;
  - hosts launched in their own units, with no =setsid= fallback;
  - editor-tool forwarding;
  - the in-process service path deleted.

  It is proved by restarting the unit with harnesses it launched still
  running.
